# 배포 & 운영

운영은 **서버실 PC 한 곳**이다. `https://aicms.pusan.ac.kr` 로 외부 공개돼 있고, 앱과 DB 가 그 서버 안 Docker 로 같이 돈다.

## 서버 접속

서버(`swedu5`, 사설 `10.125.122.162`)는 교내망 전용이라 밖에서 바로 못 닿는다. 점프호스트를 거친다.

```bash
ssh -J ojserver@code.pusan.ac.kr:8080 -p 2222 swedu-5@10.125.122.162
```

브라우저로 내부 화면을 보고 싶으면 포트 포워딩을 붙인다. **터널은 브라우저를 쓸 PC 에서 실행해야 한다.**

```bash
ssh -J ojserver@code.pusan.ac.kr:8080 -p 2222 -L 3001:localhost:3000 swedu-5@10.125.122.162
# 이후 브라우저에서 http://localhost:3001
```

앱은 `~/cms` 에 있다. 저장소를 clone 해 둔 것이고, git 은 **읽기 전용 deploy key** 로 붙는다.
`git` 명령에 `sudo` 를 쓰면 root 에는 deploy key 가 없어 실패한다. 붙이지 말 것.

## 배포 절차

CI 가 이미지를 굽고, 사람이 서버에서 올린다. 자동 배포는 없다.

1. `develop` → `main` PR 머지
2. GitHub Actions(`release-image.yml`)가 `ghcr.io/wlsgur11/pnuaicms:<7자리SHA>` 와 `:latest` 를 빌드·푸시
3. 서버에서:

```bash
cd ~/cms
git pull
./deploy.sh
```

`deploy.sh` 는 현재 배포 SHA(`.deployed-sha`)와 `origin/main` 최신 SHA 를 비교해 그 사이 커밋 목록을 보여주고, 확인을 받은 뒤 해당 태그 이미지를 pull 해서 교체한다.

롤백은 이전 SHA 를 인자로 준다.

```bash
./deploy.sh 280d2d4
```

GHCR 은 비공개라 서버에서 한 번 로그인해 둬야 한다(`read:packages` 권한 PAT). 이미 해 뒀고, 토큰이 만료되면 다시 해야 한다.

## 환경변수

이름·용도만 적는다. **실제 값은 서버 `~/cms/.env` 에만 있고 저장소에는 없다.** 전체 목록과 설명은 저장소의 `.env.example` 을 본다.

| 변수 | 용도 |
| --- | --- |
| DATABASE_URL / DIRECT_URL | `postgresql://cms:...@db:5432/cms?schema=public` (같은 값) |
| POSTGRES_PASSWORD | db 컨테이너가 만드는 계정 비밀번호. 위 URL 의 비밀번호와 같아야 함 |
| AUTH_GOOGLE_ID / AUTH_GOOGLE_SECRET | 구글 OAuth. 클라이언트는 GCP 프로젝트 `pnuaicms-497711` 소속 |
| AUTH_SECRET | NextAuth 세션 서명 |
| AUTH_URL | `https://aicms.pusan.ac.kr`. 프록시 뒤라 필수 |
| AUTH_TRUST_HOST | `true`. 없으면 로그인이 UntrustedHost 로 깨진다(아래 참고) |
| AUTH_BYPASS | `false`. 운영에서 절대 true 금지 |
| SUPER_ADMIN_EMAILS | 최초 슈퍼관리자 부트스트랩(octopus121@pusan.ac.kr) |
| DART_API_KEY / NAVER_CLIENT_ID / NAVER_CLIENT_SECRET | 기업 자동조회 |

`.env` 는 compose 의 `env_file` 로 물려 있어 **새 이미지를 배포해도 유지된다.** 값을 바꿨을 때만 `docker compose -f docker-compose.prod.yml up -d --force-recreate` 로 반영한다.

## ⚠️ 운영 주의 (가장 중요)

- **AUTH_BYPASS=false** 로 둘 것. true 면 로그인을 통째로 건너뛰어 누구나 슈퍼관리자로 들어온다. 외부에 공개된 주소이므로 학생 실명·연락처가 그대로 노출된다.
- **AUTH_TRUST_HOST=true** 가 없으면 로그인 시 화면에 "There is a problem with the server configuration" 만 뜬다. 로그를 봐야 `UntrustedHost` 라는 걸 안다. 따옴표 없이 `true`.
- **db 서비스만 따로 재시작하지 말 것.** `docker compose up -d db` 처럼 단일 서비스로 올리면 도커 네트워크가 재생성되면서 outbound NAT 규칙이 유실될 수 있다(아래 장애 사례). 항상 `docker compose -f docker-compose.prod.yml up -d` 로 전체를 올린다.
- **ufw 를 건드렸으면 그 뒤에 도커를 재시작한다.** ufw reload 가 도커 iptables 규칙을 헝클 수 있다.
- **재부팅하면 이미지가 `:latest` 로 뜬다.** compose 가 `image: ...:${TAG:-latest}` 라서, `deploy.sh`(TAG=SHA) 없이 재부팅되면 로컬에 남은 `:latest` 로 실행된다. 재부팅 전후로 도는 코드가 달라질 수 있으니, 버전을 확실히 하려면 재부팅 후 `./deploy.sh` 로 원하는 SHA 를 다시 배포한다.

## 백업

DB 가 이 서버 하나뿐이다. 백업이 유일한 안전장치다.

- `~/cms/backup-db.sh` 가 매일 03시 cron 으로 돈다(`docker exec cms_db pg_dump`).
- 결과는 `~/cms-backups` 에 14일치 보관.
- **같은 디스크에만 있다.** 디스크가 죽으면 백업도 같이 죽는다. 외부 저장소나 다른 디스크로 복사하는 걸 권장한다.
- 복구 훈련을 한 번은 해 볼 것. 실제로 필요할 때 처음 해 보면 늦다.

## HTTPS / 도메인

- 도메인 `aicms.pusan.ac.kr` → 공인 `164.125.249.76` (A 레코드). NAT 사용기간 2026-06-19 ~ 2031-06-19, 만료 시 갱신 필요.
- `/etc/caddy/Caddyfile`:

```
aicms.pusan.ac.kr {
    reverse_proxy localhost:3000
}
```

- 인증서는 Caddy 가 Let's Encrypt 로 자동 발급·갱신한다. 설정을 바꿨으면 `sudo systemctl reload caddy`.
- 인증서 발급이 실패하면 대개 외부 → 서버 80/443 이 막힌 것이다. **포트가 열린 걸 확인하기 전에는 caddy 를 반복 재시작하지 말 것.** Let's Encrypt 실패 횟수 제한(시간당 5회)에 걸린다.

## 장애 사례: 구글 로그인이 갑자기 안 될 때 (2026-07-17)

증상은 로그인 시 `error=Configuration`, 로그에 `[auth][error] TypeError: fetch failed`. OAuth 설정 문제로 보이지만 아니었다.

원인은 **compose 네트워크의 outbound NAT(iptables MASQUERADE) 유실**이었다. 컨테이너가 밖으로 나가지 못해 구글 토큰 엔드포인트 호출이 타임아웃 났다. DNS 는 도커 내장 리졸버라 멀쩡해서 더 헷갈린다.

진단 순서:

1. `.env` 값 확인 (다 들어 있으면 설정 문제 아님)
2. 호스트에서 `curl` → 200 이면 호스트 egress 는 정상
3. 컨테이너 안에서 같은 요청 → 실패하면 도커 네트워크 문제
4. `sudo iptables -t nat -S POSTROUTING` 에서 그 서브넷 MASQUERADE 규칙이 있는지 확인

조치: 네트워크가 존재하는 상태에서 `sudo systemctl restart docker` 로 규칙 재삽입. 그래도 어중간하면 `sudo reboot` 가 확실하다(부팅 때 도커가 규칙을 처음부터 만든다).

헛짚기 쉬운 것: ufw `DEFAULT_FORWARD_POLICY`, MTU. 둘 다 원인이 아니었다.
